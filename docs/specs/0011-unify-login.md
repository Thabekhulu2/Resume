# Unify Recruiter and Candidate Login Specification

**Status:** Approved
**Owner:** Ndumiso Mpanza
**Created:** 2026-09-04
**Last Updated:** 2026-09-04
**Ticket:** Closes #22

## Overview

Replace the two separate login entry points introduced in spec 0008 (`/login` for Recruitment Team, `/candidate/login` for Candidates) with a single login page. The same email/password form is used by both user types; after a successful sign-in, the existing role lookup (`recruiters`/`candidates` table membership) decides where the user lands. Candidate self-signup remains a distinct page — only the login side is merged.

## Goals

- One login route, one form: no "which kind of account are you" choice before authenticating.
- After sign-in, resolve role and redirect: recruiter -> Dashboard (`/`), candidate -> `/apply`.
- Wrong/no credentials show one inline error, same as today.
- All existing redirect-to-login points (`_authenticated.tsx`, `_candidateAuth.tsx` guards, header Logout) point at the single login route instead of branching by role.
- Candidate self-signup (`/candidate/signup`) is unaffected except its "Log in" link now points at the unified route.

## Non-Goals

- Changing how role is determined (still row-existence in `recruiters` vs `candidates`, from spec 0008) — out of scope.
- Recruiter self-signup — still manually provisioned (spec 0008 non-goal, unchanged).
- Merging candidate signup into the login page, or adding a combined signup/login toggle — candidate signup stays separate.
- Any RLS/backend change — this is a frontend routing/UI consolidation only; no database or Edge Function changes.

## User Stories

### As any user (recruiter or candidate), I want one login page so I don't have to know or guess which login URL applies to me

**Acceptance Criteria:**
- [ ] A single route (`/login`) renders one email/password form with no role selector
- [ ] `/candidate/login` no longer exists as a separate page (route removed; see Open Questions for whether it should redirect)
- [ ] Recruiter credentials land on the Dashboard after sign-in
- [ ] Candidate credentials land on `/apply` after sign-in
- [ ] Invalid credentials show an inline error, not a crash or misleading redirect
- [ ] Visiting any recruiter-only route while logged out redirects to `/login`
- [ ] Visiting any candidate-only route (`/apply`) while logged out redirects to `/login`
- [ ] Logout (from either role) redirects to `/login`

## Technical Design

### Architecture

```
frontend/src/routes/login.tsx (unchanged path, form becomes role-agnostic)
  -> signIn(email, password)          [lib/auth.tsx, unchanged]
  -> resolveRole(session.user.id)     [lib/auth.tsx, unchanged — already queries both tables]
  -> navigate({ to: role === 'candidate' ? '/apply' : '/' })

_authenticated.tsx   beforeLoad: !session -> redirect('/login')      (was: '/login', unchanged)
                                   role !== 'recruiter' -> redirect('/login')  (was: '/candidate/login')
_candidateAuth.tsx    beforeLoad: !session -> redirect('/login')      (was: '/candidate/login')
                                   role !== 'candidate' -> redirect('/login')  (was: '/login', unchanged)

__root.tsx  Header.handleLogout -> navigate({ to: '/login' })  (was: branched by role)
            PUBLIC_PATHS -> drop '/candidate/login'
```

Net effect: every redirect that used to point at `/candidate/login` now points at `/login`; the wrong-role branches in both guards collapse to the same target as the no-session branch, since there's only one login page to send anyone to.

### Changes by file

- `frontend/src/routes/login.tsx`: after successful `signIn`, call `resolveRole` (via a small helper in `lib/auth.tsx`, e.g. exposing the already-fetched role from `useAuth()` post sign-in, or re-resolving directly) and `navigate({ to: role === 'candidate' ? '/apply' : '/' })` instead of unconditionally `navigate({ to: '/' })`. Copy changes from "Recruitment Team Login" to a neutral "Log In".
- `frontend/src/routes/candidate/login.tsx`: deleted.
- `frontend/src/routes/candidate/signup.tsx`: "Log in" link target changes from `/candidate/login` to `/login`.
- `frontend/src/routes/_authenticated.tsx`: wrong-role redirect target changes from `/candidate/login` to `/login`.
- `frontend/src/routes/_candidateAuth.tsx`: no-session redirect target changes from `/candidate/login` to `/login`.
- `frontend/src/routes/__root.tsx`: `PUBLIC_PATHS` drops `/candidate/login`; `Header.handleLogout` navigates to `/login` unconditionally (drop the role-based branch).
- `frontend/src/routeTree.gen.ts`: regenerated by the TanStack Router Vite plugin once `candidate/login.tsx` is removed (as it was hand-verified against real tooling in a prior session — see project memory).

### Security Considerations

No RLS or Edge Function changes. Role resolution and its enforcement remain exactly as specified in 0008 (RLS is the real boundary; this only changes which page the UI-level route guard bounces an unauthorized user to). Removing `/candidate/login` as a route means any bookmarked/hardcoded links to it 404 — acceptable since this is an internal-stage tool with no external users yet (confirmed by current test-account-only usage).
