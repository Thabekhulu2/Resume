# Implementation Plan: Spring Boot + Angular Migration

**Spec:** [0018-springboot-angular-migration.md](./0018-springboot-angular-migration.md)
**Ticket:** Closes #29
**Status:** Approved (Gate 1)

## Resolving the spec's open questions

- **Module layout**: single Spring Boot Maven/Gradle module (`backend/`) containing the REST API, Spring Security config, and an embedded Temporal worker (started via a `@Component`/`CommandLineRunner`, same "worker lives in the same process as the trigger" shape the Python side used). No separate worker module — simplest option, matches current deployment shape (one `temporal-worker` container).
- **Credential storage**: `recruiters`/`candidates` currently FK to `auth.users(id)` and hold no password — GoTrue owns credentials entirely. Since Supabase Auth is being dropped, this plan adds a migration (`supabase/migrations/<ts>_decouple_auth_from_supabase.sql`) that:
  - Drops the `references auth.users(id)` FK on both tables (keeps `id uuid primary key`, now app-generated).
  - Adds `email text unique not null` and `password_hash text not null` to both tables.
  - Drops the `handle_candidate_signup` trigger/function and the RLS policies that reference `auth.uid()` (dead once Spring Boot connects as its own DB role and enforces auth at the API layer instead of RLS).
  - **Known limitation, called out explicitly**: existing local dev accounts' passwords live in GoTrue and are not recoverable — they must be recreated (re-signed-up) against the new Spring Boot auth once it's live. This is acceptable for local/dev data; flag to the user before cutover in case any account matters.
  - Spring Security uses a JDBC-backed `UserDetailsService` (via `recruiters`/`candidates`, `BCryptPasswordEncoder` for `password_hash`) plus JWT issuance for stateless API auth (Angular sends `Authorization: Bearer`).
- **Supabase CLI's role**: kept solely as the local Postgres provider (`supabase start` for the DB container). Studio/Auth/Storage/Realtime/Edge Functions are not started or are ignored once the new stack is up; `docker-compose.yml` stops depending on them.

## Phase 1: Auth decoupling migration + Spring Security

- [x] Migration `supabase/migrations/20260914090000_decouple_auth_from_supabase.sql`: drops the `auth.users` FK on `recruiters`/`candidates`, adds `email`/`password_hash` (backfilled for any pre-existing rows, then tightened to `not null unique`), drops `handle_candidate_signup`/its trigger and the two `select own row` RLS policies.
  - **Bug found and fixed beyond the plan's original description**: `entities.applicant_id` and `notifications.recipient_id` also FK'd to `auth.users(id)` (storing what was always `candidates.id`, back when `candidates.id` *was* the `auth.users.id`). Once `candidates.id` became independently generated, any new candidate created via Spring Boot would have no `auth.users` row at all — inserting their id into either column would violate the FK and fail outright. Repointed both FKs at `candidates(id)` instead (existing data is unaffected since the UUID values themselves don't change, only the referenced table).
  - Also seeded one local dev recruiter account (`recruiter@resume.local` / `password123`, bcrypt-hashed) since recruiter accounts were previously provisioned manually via Supabase Studio's Auth UI, which no longer exists in this flow — there was otherwise no way to create a recruiter account at all under the new stack. Recruiter self-signup stays out of scope, matching the original "provisioned manually" design.
- [x] Spring Security (`backend/src/main/java/com/resume/backend/auth/`): `Recruiter`/`Candidate` JPA entities + repositories, `BCryptPasswordEncoder`, `JwtService` (jjwt, HMAC-signed, `sub`=id/`role`/`email` claims), a stateless `JwtAuthenticationFilter` populating `SecurityContextHolder` from the `Authorization: Bearer` header. `SecurityConfig` updated: stateless sessions, `/api/health` + `/api/auth/**` open, everything else requires a valid JWT (per-role `hasRole(...)` restrictions added as domain endpoints land in later phases).
- [x] Endpoints: `POST /api/auth/recruiter/login`, `POST /api/auth/candidate/login`, `POST /api/auth/candidate/signup` (`AuthController`) — login returns generic 401 on either unknown email or wrong password (no user enumeration), signup 409s on duplicate email.

- `mvn compile` — clean.
- New unit tests, all passing (`mvn test`): `JwtServiceTest` (3 — issue/parse round trip, garbage token rejected, token signed with a different secret rejected) and `AuthControllerTest` (5 — recruiter login success/wrong-password/unknown-email, candidate signup duplicate-email/success), using Mockito against the repositories (no live DB needed for these).
- Migration SQL manually re-checked against the actual prior migrations' auto-generated constraint names (`recruiters_id_fkey`, `entities_applicant_id_fkey`, `notifications_recipient_id_fkey`) to confirm the `drop constraint` statements target the real names.
- **Live e2e verification (Docker started this session)**: `supabase db reset --local` applied all 14 migrations cleanly, including the new one, against the real local Postgres. Started the Spring Boot backend against it (`DB_URL=jdbc:postgresql://127.0.0.1:55322/postgres`) and exercised the real HTTP endpoints:
  - Recruiter login with the seeded `recruiter@resume.local`/`password123` → 200 + valid JWT; verified the JWT's `sub`/`role`/`email` claims decode correctly.
  - Candidate signup (`newcandidate@resume.local`) → 201-equivalent (200 + JWT), row confirmed via `psql` directly against `candidates` (correct `id`/`full_name`/`email`, `password_hash` is a real 60-char bcrypt hash, not plaintext).
  - Adversarial: wrong password and unknown email both → 401 (generic message, no enumeration); duplicate-email signup → 409; candidate login with the freshly-created account → 200; a protected path with no `Authorization` header, and with a garbage bearer token, both → 403 (denied, not silently allowed).
  - **A real bug live-testing caught that the mocked unit tests couldn't**: Spring MVC's internal forward to `/error` (used to render a thrown `ResponseStatusException`, e.g. the controller's 401s) re-enters the same Spring Security filter chain. Fixed by adding `/error` to `SecurityConfig`'s permitted paths. Re-verified after the fix: wrong-password/unknown-email now correctly return 401 (previously 403), everything else unchanged.

## Phase 2: Core data access layer

- [x] JPA entities (`backend/src/main/java/com/resume/backend/core/`) mapping the existing generic SCD2 model as-is, no schema changes: `EntityRecord`→`entities` (named `EntityRecord` to avoid clashing with `jakarta.persistence.Entity`), `EntityVersion`→`entity_versions` (`data` mapped as `Map<String,Object>` via Hibernate 6's native `@JdbcTypeCode(SqlTypes.JSON)`, `is_current`/`created_at` read-only — entirely trigger-managed), `Relationship`→`relationships_v2`, `FactType`→`fact_types` (read-only lookup), `EntityFact`→`entity_facts` (mapped for reads; writes go through a native upsert, see below).
- [x] `CoreEntityService` replicates `supabase_core.py`'s five functions as `@Transactional` methods: `createEntity`, `updateEntityScd2` (relies on the existing `set_entity_version_validity` DB trigger to close the prior current version — just inserts the next row, exactly like the Python side), `getEntity` (returns a new `EntitySnapshot` record), `createRelationship`, `upsertEntityFact` (JPA has no clean `ON CONFLICT` support, so this is a native query matching the Python side's `.upsert(..., on_conflict="entity_id,fact_type_id,dimension_id")` exactly, including the same conflict target columns).
- [x] Confirmed the open question from Phase 1/2 planning: the `postgres` role (Spring Boot's default local `DB_USERNAME`) is the Supabase-CLI stack's superuser and bypasses RLS/grants entirely — no new DB role or grant changes were needed for direct table access to work.

**Verification performed**:
- `mvn compile` — clean.
- 8 new unit tests (`CoreEntityServiceTest`, Mockito-mocked repositories/`EntityManager`) — all passing: entity+version creation, SCD2 version-number increment, missing-current-version failure, entity+version combination in `getEntity`, missing-entity failure, relationship field mapping, fact upsert's native-query parameter binding, unknown-fact-type failure.
- **Live integration test against the real local Postgres** (temporary `@SpringBootTest`, run once via `mvn test` then deleted — same throwaway pattern as Phase 1's bcrypt-hash generator): full lifecycle exercised for real — `createEntity` → `getEntity` (version 1, correct data) → `updateEntityScd2` → `getEntity` again (version 2, new data, confirming the SCD2 trigger actually closed the old version) → `createRelationship` → `upsertEntityFact` twice with different values (second call returned the *same* fact id as the first, confirming the `ON CONFLICT` target genuinely matched and updated in place rather than erroring or duplicating). Ran inside `@Transactional` so Spring Test auto-rolled-back afterward; confirmed via `psql` that zero rows were left behind.

## Phase 3: File storage (replacing the `resumes` Storage bucket)

- [x] `ResumeStorageService` (`backend/src/main/java/com/resume/backend/storage/`): local filesystem storage under `resumes.storage-dir` (`/data/resumes` in the container, the volume already wired up in Phase 0). Files are laid out as `{root}/{uploaderRole}/{uploaderId}/{uuid}__{originalFilename}` — ownership is derivable from the id string alone, so no new DB table was needed for it. Rejects empty files and anything other than `.pdf`/`.docx`; guards against path traversal, including the classic `Path.resolve()`-with-an-absolute-argument bypass (an id like `/etc/passwd` would otherwise ignore `root` entirely).
- [x] `ResumeController`: `POST /api/resumes` (multipart upload, returns `{id, filename}`) and `GET /api/resumes/{*id}` (streams the file back with the original filename in `Content-Disposition`). Candidates may only fetch resumes they uploaded themselves (403 otherwise); recruiters may fetch any resume, mirroring the old `resumes recruiters select` Storage policy. This replaces both the frontend's direct Storage `upload()` call and the `get-my-resume-url` Edge Function.
- [x] `spring.servlet.multipart.max-file-size`/`max-request-size` set to 10MB in `application.yml` (Spring Boot's default is 1MB, too small for real resumes).

**Verification performed**:
- `mvn compile` — clean.
- 7 new unit tests (`ResumeStorageServiceTest`, using `@TempDir` + `MockMultipartFile`, no DB needed): store/load round trip preserves content and original filename, empty-file rejection, disallowed-extension rejection, `isOwnedBy` matches only the exact role+id, path-traversal rejection (`../../etc/passwd`), absolute-path-id rejection (`/etc/passwd`), missing-file 404 case.
- **Live e2e + adversarial verification** against the real backend + live Postgres (recruiter + two fresh candidates, real JWTs): candidate A uploads → downloads their own file successfully with byte-for-byte matching content and the correct `Content-Disposition` header; candidate B → 403 on candidate A's file; recruiter → 200 on candidate A's file (cross-role access confirmed); no `Authorization` header → 403; disallowed extension (`.exe`) → 400; empty file → 400; path traversal via the URL (`/api/resumes/../../../../etc/passwd`) → 404 (denied, not served); a real ownership mismatch on a well-formed but wrong id → 403 (checked before existence, so it doesn't leak which resumes exist); a genuinely missing file under the caller's own folder → 404 (the actual not-found case, distinct from the ownership-mismatch 403 above).
  - **A real bug live-testing caught that the unit tests couldn't**: the original implementation extracted the wildcard id via the legacy `HandlerMapping.PATH_WITHIN_HANDLER_MAPPING_ATTRIBUTE` + `AntPathMatcher.extractPathWithinPattern` idiom. Spring Boot 3's default `PathPatternParser`-based request matching leaves that attribute's value percent-encoded — a filename with a space came back as `...%20...` instead of `... ...`, so any resume whose original filename contained a space (an extremely common case) could be uploaded but never downloaded again (spurious 404). Fixed by switching to Spring 6's `@GetMapping("/{*id}")` + `@PathVariable String id` capture, which goes through normal URI decoding. Re-verified: a space-containing filename now uploads and downloads correctly.
  - Test data (candidate accounts, uploaded files, scratch storage dir) cleaned up after verification.

## Phase 4: Temporal Java SDK worker (scoring workflow)

- [x] **Correction to this bullet's original wording**: re-reading the actual current Edge Function (`supabase/functions/start-scoring-workflow/index.ts`) before implementing showed bulk scoring does **not** stop on first failure — spec 0004 (ticket, commit `fb5e677`) changed it to continue past a failing resume, collecting a `failures[]` list alongside `candidates[]`. Implemented to match the *real* current behavior, not the plan's outdated description.
- [x] Small necessary extension to Phase 2: `CoreEntityService.createEntity` gained an overload accepting an optional `applicantId` (`EntityRecord` gained the matching `applicant_id` column mapping), since the Edge Function's `scoreOneResume` sets it for candidate self-applications. 2-arg call sites (existing `CoreEntityServiceTest`) unaffected.
- [x] `backend/src/main/java/com/resume/backend/scoring/`: Temporal boundary types are plain mutable POJOs (getters/setters, no records) — the Python-side "typing gotcha" memory made this the safer default for anything Temporal serializes, even though the risk profile differs for Java/Jackson.
  - `ResumeParsingActivities`/`Impl`: PDFBox (`Loader.loadPDF` + `PDFTextStripper`) for `.pdf`, Apache POI (`XWPFDocument`, paragraph-by-paragraph join) for `.docx`, reading from Phase 3's `ResumeStorageService` — matches `resume_parsing.py` exactly, including the unsupported-extension error.
  - `ScoringActivities`/`Impl`: same prompt template, calls Anthropic (`RestClient`, `x-api-key`/`anthropic-version` headers) or local Ollama (`USE_LOCAL_LLM`) depending on config. Shape validation extracted into a standalone `ScoreResponseParser` (testable without HTTP) matching `_validate_and_parse` field-for-field, including the Python `isinstance(x, bool)` exclusion on `score` — in Java this falls out for free since Jackson's `BooleanNode.isNumber()` is `false`, no special-casing needed.
  - `CoreEntityActivities`/`Impl`: thin wrapper around `CoreEntityService` (Phase 2), converting `UUID`↔`String` at the boundary.
  - `ScoreResumeFitWorkflow`/`Impl`: same control flow as `workflow.py` — extract → score → create-or-update candidate → create relationship → upsert fact; on failure, walks `getCause()` to the root (Java's `ActivityFailure`→`ApplicationFailure` chain, same idea as Python's `exc.__cause__` walk), fetches the current entity, merges in `status: failed` + `error`, and rethrows.
  - `TemporalConfig`: `WorkflowServiceStubs`/`WorkflowClient`/`WorkerFactory` beans, registers the workflow type + activity impl beans on the `main` task queue, starts the factory at context startup.
  - `ScoringController`: `POST /api/scoring/start`, porting the *entire* Edge Function's orchestration (not just the workflow trigger) — resolve-or-create the `job_description` entity, batch vs. singular handling, per-resume candidate creation, starting the workflow asynchronously via `WorkflowClient.start(...)` (fire-and-forget, matching the Python/TS side never awaiting workflow completion).

- **Live e2e against the real stack**: real local Postgres, the real `resume-temporal` server (Java worker connected via `localhost:57234`, pollers started for both the Workflow and Activity task queues on `main`), and a real local Ollama (`qwen2.5:7b`) — no mocks anywhere in this pass.
  - Generated two real `.docx` fixtures via Apache POI, uploaded both through Phase 3's `/api/resumes`, then `POST /api/scoring/start` with both paths in one `resumeStoragePaths` batch against a new job (`jdText`+`jobTitle`). Both candidates transitioned `scoring` → `scored` asynchronously; extracted `name`/`skills`/`experience` were correct and **not cross-contaminated** between the two candidates processed in the same batch (a real concurrency/isolation check, not just a shape check) — Alice Johnson's Java/Spring Boot/PostgreSQL skills stayed with her record, Bob Smith's Angular/TypeScript stayed with his. Real fit scores (90, and a lower score for the frontend candidate against a backend JD) with coherent LLM-generated reasoning. `entity_facts` row and `candidate_scored_against_job` relationship both confirmed correct via direct Postgres queries.
  - **Job-description reuse**: a third resume submitted with an existing `jobDescriptionEntityId` (no `jdText`) correctly resolved `jd_text` server-side and did **not** create a duplicate `job_description` entity (confirmed via count query) — matches the Edge Function's reuse path.
  - **Adversarial — the "failed" status path, isolated**: restarted the backend pointed at a deliberately broken Ollama URL, submitted a real resume for scoring. The `extractAndScore` activity (the one activity with a bounded `maximumAttempts=3` retry policy) failed 3 times and the workflow's catch block correctly unwrapped the root cause and wrote `status: failed` + a real error message to the candidate entity — confirmed via direct Postgres query. This is the first real, non-mocked proof the Java root-cause-unwrap-and-mark-failed logic actually works end-to-end.
  - **Adversarial — HTTP validation**: missing `resumeStoragePath`/`resumeStoragePaths` → 400; nonexistent `jobDescriptionEntityId` → 404; unauthenticated request → 403.
  - **Incidental finding, not a Phase 4 regression**: an earlier test run accidentally submitted empty-string resume paths (a curl scripting mistake, not a server bug), which caused `extractResumeText` to fail and retry *indefinitely* rather than reaching `status: failed`. Only `extract_and_score` has a bounded retry policy on both sides, which is exactly the scenario the adversarial test above exercises. Documented here rather than "fixed", since changing it would be a behavior change beyond this migration's scope (re-platform, not redesign).
  - Test data (candidate/job entities, facts, relationships, scratch resumes) cleaned up afterward; 3 zombie workflow executions from the incidental empty-path finding remain in the local Temporal server's task queue (server-side retry state only, no worker actively consuming CPU) — harmless local-dev residue, not worth chasing down `tctl`'s connectivity inside the container for.

## Out of scope

## Dependencies between phases

Phase 0 must land first. Phase 1 (auth) blocks Phase 5's recruiter/candidate-scoped endpoints and all of Phase 6. Phase 2 (data layer) blocks Phases 4 and 5. Phase 3 (storage) blocks Phase 4 (resume text extraction needs storage to read from). Phase 4 blocks the scoring parts of Phase 5. Phase 6 depends on Phases 1, 3, 4, 5 all being far enough along to have real endpoints to call — in practice built incrementally per-page against whichever endpoints already exist, rather than strictly after Phase 5 finishes entirely. Phase 7 (cutover) only happens once Phase 8 verification passes. Given the size of this migration, each phase will be committed and Gate-2-approved separately rather than as one giant commit at the end.
